/delegate 효과 점검

무엇을 하려던 건지

비싼 상위 모델(Opus 5.5)은 관리자로서 계획·판정·구원만 맡고, 실제 코딩은 싼 하위 모델(Sonnet 5, Haiku 4.5) 작업자에게 맡겨 비용을 아끼자는 구조. 처음엔 Codex를 작업자로 쓰는 안을 조사했지만, 구독이 없어서 Claude Code만으로 /delegate(작업 단위)와 /delegate-all(프로젝트 단위) 두 스킬을 만들었다.

설계 방향은 외부 근거와 잘 맞는다. 하지만 첫 실사용에서 비용 절감은 거의 없었다 — 원인은 모델 선택보다 “관리자 대화의 무게”였다.

근거: 공식 블로그·연구·커뮤니티 측정 7건 + 실사용 프로젝트 실제 /delegate 실행 기록(토큰 사용량 직접 집계).

실측실사용 프로젝트에서 실제로 돌려본 결과

작업: 앱의 한글 표시(팀명·리그명·실시간 상태·UI 문구)를 영어 사용자용으로 전환. 2026-09-24 실행.

이번 점검에서 새로 알게 된 것

“관리자는 토큰을 아낀다”는 목표가 실측에선 지켜지지 않았다

관리자의 출력이 작업자 8명 합계보다 많았고, 호출 수는 21%인데 토큰은 43%를 썼다. 모델을 싼 걸로 바꾸는 것보다 관리자를 가벼운 새 대화에서 시작하는 것이 더 큰 절약 수단일 가능성이 크다. 또 이번엔 관리자·작업자가 모두 Sonnet이라 “싼 모델로 나누기” 효과 자체가 없었다 — 이 실행에서 얻은 건 비용 절감이 아니라 병렬 처리와 검증 구조였다.

수정 이력만들면서 발견하고 고친 문제

  1. 스킬의 모델 설정은 “그 응답 한 번”에만 적용

    승인 메시지를 보내는 순간 관리자가 세션 모델(Sonnet)로 돌아감 — 세션 기록으로 확인.

    → 계획 끝에 “승인 전 앱 모델 선택기를 Opus 5.5로” 안내 + 관리자가 자기 모델을 밝힘 (v0.4)
  2. 파일 앞의 보이지 않는 표식(BOM)

    PowerShell 저장 방식 때문에 붙어서 스킬 설정이 무시될 위험.

    → 전부 제거, 저장 방식 메모리에 기록
  3. 호출 횟수 상한(8회)이 일을 뭉치게 만듦

    관리자가 횟수를 아끼려 한 작업자에게 여러 화면을 몰아주고, 상한 기준도 8↔10으로 흔들림.

    → 첫 시도는 세지 않고 재시도만 제한, 계획에 적힌 숫자가 공식 상한 (v0.5)
  4. 밤모드 규칙과 충돌

    밤모드는 “코드 반영 보류”, /delegate-all은 “승인된 마일스톤은 밤에도 진행”.

    → 둘 중 하나만 켜기, 답 없으면 밤모드 쪽(안전)이 기본

다음남은 것과 결정할 것

참고

재시도 예산 조정

첫 실측에선 재시도가 0회라 4회(/delegate)·12회(/delegate-all)는 넉넉한 편. 몇 번 더 써보고 조정.

실측 수치는 실사용 프로젝트 세션 기록(메인 대화 + 작업자 8명)의 토큰 사용량을 직접 합산한 값이며, 한 번의 실행이라 일반화하기엔 표본이 작다. 외부 수치(90%, 15배, 40~52%, 98%)는 각자 다른 작업·조건에서 나온 값이라 코딩 작업에 그대로 적용된다는 보장은 없다.
