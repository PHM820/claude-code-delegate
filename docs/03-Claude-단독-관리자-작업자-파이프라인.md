# Claude Code만으로 만드는 관리자–작업자 파이프라인

> 작성일: 2026-09-24 · Codex 구독이 없을 때의 대안 (02 문서의 Codex 자리를 Claude 하위 모델로 교체)
> 구성: **관리자 = Opus 5.5 (메인 세션)** / **작업자 = Sonnet 5, Haiku 4.5 (서브에이전트)**

---

## 1. 핵심 — 필요한 기능이 전부 Claude Code에 내장돼 있다

공식 문서(code.claude.com/docs/en/sub-agents)에서 확인한 서브에이전트 정의 파일(`.claude/agents/*.md`) 필드 중 이 파이프라인에 쓰는 것:

| 필드 | 값 | 파이프라인에서의 역할 |
|---|---|---|
| `model` | `sonnet`, `haiku`, `opus`, 전체 ID(`claude-opus-5-5`), `inherit` | **작업자 등급 지정** |
| `effort` | `low` ~ `max` | 작업자별 추론 강도 (싼 작업은 low) |
| `maxTurns` | 정수 | **헛돌기 차단** — 한도 도달 시 "partial" 표시로 반환, 이어서 재개 가능 |
| `isolation` | `worktree` | 작업자별 git worktree 자동 분리 (변경 없으면 자동 정리) |
| `tools` / `disallowedTools` | 도구 목록 | 작업자 권한 제한 (예: `Agent` 빼서 재위임 금지) |
| `permissionMode` | `acceptEdits` 등 | 작업자가 파일 수정 시 매번 묻지 않게 |
| `hooks` | `Stop`(→ 서브에이전트에선 `SubagentStop`으로 변환), `PostToolUse` 등 | **자동 판정기 연결 지점** |
| `skills` | 스킬 이름 | 작업 규칙(리포트 형식 등)을 작업자에게 미리 주입 |

추가로:
- **모델 결정 순서:** 호출 시 `model` 인자 → 정의 파일의 `model` → 환경변수 `CLAUDE_CODE_SUBAGENT_MODEL` → 메인 모델. 즉 **관리자가 호출할 때 `model: "opus"`로 덮어써서 같은 작업자를 상위 모델로 올릴 수 있다** — 이것이 에스컬레이션의 핵심 수단.
- **SendMessage:** 끝난 작업자를 문맥 그대로 이어서 부를 수 있음 → "같은 작업자에게 에러 알려주고 재시도"가 싸게 가능.
- **문맥 격리:** 일반 서브에이전트는 대화 이력을 물려받지 않고 새 문맥에서 시작, 결과만 돌려준다 → 작업자의 긴 로그·시행착오가 **관리자(Opus) 문맥에 쌓이지 않음**. 비용 절약의 본체.
- 동시 실행 기본 한도 20개, 중첩 깊이 기본 3단.

## 2. 에스컬레이션 사다리

```
[0] Opus 관리자: 작업 분해 + 작업 지시서 작성 + 난이도별 작업자 선택
      단순(검색·반복 수정·테스트 보강) → worker-light (Haiku 4.5)
      일반 구현                         → worker (Sonnet 5)
         │
[1] 작업자 실행 (worktree 격리, maxTurns 제한)
         │ 끝나려는 순간 SubagentStop 훅이 테스트 실행
         │ 실패 → 1회만 종료 차단 + 에러 끝부분을 작업자에게 되먹임 (관리자 개입 없음, 자동 재시도)
         ▼
[2] 작업자가 JSON 리포트 반환 → 관리자는 리포트만 읽음
      통과 → 완료
      실패 → 관리자 판단 (싼 것부터):
         a. SendMessage로 같은 작업자에게 힌트 한 줄 주고 이어서 (문맥 재사용, 가장 쌈)
         b. Haiku였다면 → 같은 지시서로 worker(Sonnet)에 재위임
         c. Sonnet도 실패 → 같은 작업자를 model: "opus"로 덮어써서 재위임
         ▼
[3] ★ Opus 관리자 직접 구원 ★ — diff + 에러 요약 보고 직접 수정
         ▼
[4] 관리자도 2번 실패 → 사용자에게 보고, 중단 (상태는 worktree·리포트로 보존)
```

규칙: 각 단계는 **최대 2회** (사용자 CLAUDE.md "2번 실패하면 목적부터 다시 본다"와 동일). 같은 등급에서 3번째 시도는 금지 — 올리거나 멈춘다.

## 3. 파일 구성 (프로젝트에 넣을 것)

```
<대상 프로젝트>/
├─ .claude/
│  ├─ agents/
│  │  ├─ worker.md          ← Sonnet 5 구현 작업자
│  │  └─ worker-light.md    ← Haiku 4.5 단순 작업자
│  ├─ skills/
│  │  └─ delegate/SKILL.md  ← 관리자용 절차: 지시서 → 위임 → 판정 → 사다리
│  └─ settings.json         ← (선택) 세션 전체 훅
└─ scripts/
   └─ verify.ps1            ← 판정기: 테스트/빌드 실행, pass/fail + 사유 3줄만 출력
```

템플릿은 이 폴더의 `templates/agents/`에 있음.

### 3-1. 작업자 리포트 형식 (작업자 시스템 프롬프트에 강제)

작업자는 응답 마지막을 반드시 아래 JSON 한 덩어리로 끝낸다. 관리자는 이것만 읽는다.

```json
{"status":"done|failed|blocked","changed_files":["..."],"verify":"실행한 명령과 결과 한 줄","summary":"600자 이내","blocker":"막힌 이유(있을 때만)"}
```

`status:"done"`은 참고용. 성공 판정은 판정기(`verify.ps1`) 결과로만 한다(가짜 완료 방지).

### 3-2. 자동 재시도 훅 — 작업자 정의 안에

```yaml
hooks:
  Stop:          # 서브에이전트에서는 SubagentStop으로 동작
    - hooks:
        - type: command
          command: "powershell -File ./scripts/verify.ps1"
```

판정기가 실패 시 **종료코드 2 + stderr에 에러 요약**을 내면 작업자가 멈추지 않고 그 에러를 받아 계속 고치게 된다.
⚠️ 무한 루프 방지 필수: 훅 입력의 `stop_hook_active`가 true면(이미 한 번 되먹임했으면) 그냥 통과시켜 작업자가 `failed` 리포트로 끝내게 한다. (이 차단 동작·필드명은 hooks 문서 기준 설계이며 실제 동작은 1단계 체험 때 확인 필요)

## 4. 비용 관점 — Codex 방식과 무엇이 다른가

| 항목 | Codex 워커 방식 (02) | Claude 단독 방식 (03) |
|---|---|---|
| 작업자 비용 | ChatGPT 구독 한도 (별도 주머니) | **같은 Claude 구독 한도** 안에서 차감 |
| 절약 원리 | 비싼 작업을 다른 회사 한도로 이전 | 비싼 Opus 대신 Sonnet/Haiku가 토큰 대부분을 씀 + 작업자 로그가 Opus 문맥에 안 쌓임 |
| 교차 검증 | 다른 회사 모델끼리 → 맹점 적음 | 같은 계열 → 맹점 겹칠 수 있음 → **판정은 테스트 스크립트로** |
| 설치·연동 | 플러그인 + Codex 로그인 | 추가 설치 없음 |
| 제어 세밀도 | 플러그인 경유라 간접적 | 모델·턴수·권한·훅 전부 정의 파일로 직접 |

가성비가 사는 조건:
- 관리자(Opus)는 **지시서 작성, 리포트 읽기, 구원** 세 순간에만 토큰을 쓴다. 작업자 결과를 Opus가 다시 전부 읽으면 절약이 사라진다.
- 작은 작업(몇 줄 수정)은 위임 오버헤드가 더 크다 → Opus가 직접. 위임 기준선 예: "파일 3개 이상 또는 테스트 작성 포함".
- 병렬은 서로 독립인 작업에만. 동시 20개까지 가능하지만 한도 소진이 빨라지므로 실사용은 2~3개.

## 6. 도입 순서

1. 템플릿 두 개를 실제 프로젝트(예: traffic-light-map) `.claude/agents/`에 복사
2. 작은 작업 2~3개를 "worker에게 맡겨"로 수동 위임 → 리포트 형식 지켜지는지, Sonnet 품질 체감
3. `verify.ps1` 작성 후 훅 연결 → 자동 재시도·루프 방지 동작 확인
4. 관리자 절차를 `delegate` 스킬로 정리 (사다리 규칙 포함)
5. 병렬 worktree 2개로 확장

## 검증 수준
- **공식 문서로 확인:** 정의 파일 필드, 모델 결정 순서, 동시·중첩 한도, Stop→SubagentStop 변환, 문맥 격리
- **설계상 맞다고 보지만 미검증:** SubagentStop 훅 종료코드 2로 작업자 재시도시키는 동작과 `stop_hook_active` 루프 방지, 실제 비용 절감 폭
