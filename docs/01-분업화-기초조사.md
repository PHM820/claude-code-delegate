# 1. Executive Summary  
**핵심 결과:** Claude Code는 AI 코딩 어시스턴트 환경으로, 코드를 작성·실행하고 간단한 디버깅 기능을 제공. 그러나 “최상급 모델이 관리·감독하고 하위 모델들이 실제 작업을 수행”하는 완전한 계층형 멀티에이전트 시스템 기능은 공식 지원되지 않는다. 현재로서는 Claude Code 내부에 subagent를 생성하거나 여러 모델을 자동으로 조합하는 기능은 명시적으로 제공되지 않으며, 복잡한 작업 분해·라우팅·에러 처리·승격(escalation) 구조는 추가 오케스트레이션 계층을 통해 구축해야 한다.  
- **가능성:** Claude Code 자체로는 단일 모델 세션 내에서 작업을 자동 분배·병렬 실행하거나 모델 간 전환 기능이 제한적이다. 그러나 외부 오케스트레이터(예: LangChain, AutoGen 등)를 사용하면, 여러 Claude 세션(또는 다른 경량 모델 세션)을 조합하여 관리자-작업자 구조를 구현할 수 있다.  
- **제약 사항:** 작업 실패 감지나 재시도 로직은 주로 외부에서 구현해야 하며, Claude Code 내부에서 자동 전환이나 작업 상태 추적 기능은 부족하다. 파일 공유 및 동시 수정 충돌 방지, 권한 제어 등은 Claude Code 외부의 Git·컨테이너·CI/CD 도구 등을 동원해야 실용적이다.  
- **추천 방향:** 중첩된 multi-agent 구조는 공식 기능만으로는 불가능할 수 있으나, Claude Code와 함께 사용할 수 있는 오픈소스 멀티에이전트 프레임워크(예: LangChain, AutoGen) 및 DevOps 도구(Docker, Git, Kubernetes 등)를 결합해 설계할 수 있다. 예컨대 낮은 신뢰도 작업을 가벼운 모델에 맡기고, 실패 시 클라우드 API(Claude 또는 GPT 등)로 escalation하는 하이브리드 구조가 유망하다.  

> **결론:** 현재 Claude Code의 공식 기능만으로 완전한 계층형 자율 에이전트 시스템을 구현하기는 어려우나, 모델별 역할 분담과 자동화의 핵심 아이디어는 주로 외부 오케스트레이션 계층을 통해 현실화할 수 있다. 작업 분해, 여러 세션 조합, 실패 감지 및 재시도 로직 등은 추가 도구와 코드로 보완해야 하며, 특히 보안과 충돌 방지에 유의해야 한다.  

# 2. 핵심 개념 정의  
- **Manager Agent (감독 에이전트)**: 전체 워크플로우를 관리·조정하는 최상위 모델. 작업을 분해하고 하위 에이전트에 할당하며, 결과를 검토해 최종 결정을 내린다. 예를 들어 요구사항 분석, 작업 계획 작성, 결과 평가 등 핵심 의사결정 역할을 수행한다.  
- **Worker Agent (작업 에이전트)**: 구체적 하위 작업을 수행하는 모델. 코드 작성, 테스트 실행, 자료 조사 등 실제 작업을 담당한다. 여러 워커가 병렬로 특정 역할(예: 코딩, 테스트, 문서화)을 맡을 수 있다.  
- **Supervisor Agent (감독자 에이전트)**: 주로 Manager와 유사한 최상위 역할을 가리키며, Manager-Agent 또는 Validator-Agent라고도 한다. 작업 흐름을 감시하고 필요 시 개입(승격)하는 역할이다. 때로 Manager와 같은 의미로 사용될 수 있다.  
- **Subagent (서브에이전트)**: 에이전트 내부에서 분기된 작은 에이전트 또는 태스크 단위. Claude Code가 공식으로 제공하는지 확인되지 않았으나, 일반적으로 하나의 에이전트가 분해된 작업을 맡도록 새로운 세션이나 역할로 파생된 에이전트를 가리킨다.  
- **Orchestrator (오케스트레이터)**: 복수 에이전트 간 조정과 워크플로우를 실행하는 외부 시스템. Claude Code 외부에서 작업 할당, 모니터링, 결과 통합 등을 구현하는 역할이다. 예: LangChain Agent나 CI/CD 시스템, 커스텀 파이썬 서버 등이 Orchestrator가 될 수 있다.  
- **Model Router (모델 라우터)**: 작업의 특성에 따라 적절한 모델/에이전트로 라우팅하는 역할. 입력 텍스트, 작업 난이도, Confidence 등을 기준으로 어느 모델이 처리할지 결정하는 로직을 의미한다. 예: 단순 수정은 저비용 모델, 복잡한 문제는 고성능 모델로 라우팅.  
- **Escalation (승격, 에스컬레이션)**: 작업 실패 또는 불확실 상황 시 상위 단계(더 큰 모델, 관리자, 사람)로 넘기는 과정. 예를 들어 저성능 모델이 해결하지 못한 문제를 중간급 모델, 해결 안 될 시 최상급 모델이나 인간이 처리하도록 순차적으로 승격한다.  
- **Human-in-the-loop (인간 개입)**: 에이전트 시스템에서 자동화되지 않고 인간이 직접 개입하는 단계. 주로 자동 처리가 어려운 불확실 영역이나 최종 검증에 사용된다.  
- **Validator Agent (검증 에이전트)**: 하위 작업 결과를 검토 및 검증하는 역할의 에이전트. 별도의 모델로 구현할 수도 있고 Manager가 이 역할을 겸할 수도 있다. 예: 코드 리뷰 전문 모델이 수정 사항을 검토하여 문제를 찾아낸다.  
- **Hierarchical Multi-Agent System (계층형 멀티에이전트 시스템)**: 여러 대의 AI 에이전트가 계층 구조로 조직되어 각자 역할을 분담하고 협력하는 시스템. 관리자, 작업자, 검증자 등 상이한 수준의 역할이 있는 형태를 말한다. 예를 들어, [Manager → Workers → Validators] 구조.  

# 3. Claude Code 공식 기능 조사  
Claude Code(현재 Claude DevTools 또는 유사 환경)는 AI 기반 코드 작성 및 실행 툴로 알려져 있다. 공식 문서에 따르면 코드 작성, 파일 편집, 터미널 명령 실행 등의 기능이 제공되며, 대화형 인터페이스에서 코딩 작업을 수행할 수 있다. 그러나 **멀티에이전트** 및 **subagent** 관련 기능은 명확히 언급되지 않는다. 주요 특징과 제약을 요약하면 다음과 같다.  

- **Subagent 지원 여부:** Claude Code 공식 문서나 릴리스 노트에서 “subagent”라는 개념은 언급되지 않는다. 현재 Claude Code 세션은 단일 에이전트(모델)로 동작하며, 에이전트를 내부에서 분할(subagent)하는 기능은 공개되지 않았다.  
- **모델 지정:** Claude Code 인터페이스나 API 호출 시 사용할 모델(Claude 3 Opus, Claude 3 Sonnet 등)을 지정할 수 있다. 하지만 한 세션 안에서 *다른 모델로 전환*하는 기능은 제공되지 않는다. 즉, 세션 생성 시 선택한 Claude 모델을 변경하려면 새 세션을 시작해야 한다.  
- **시스템 프롬프트:** Claude Code 내에서 관리자나 작업자별로 별도의 시스템 프롬프트를 정의하는 기능은 공식 문서에 나타나지 않는다. 현재까지는 주로 사용자 입력과 생성 모델의 응답만 사용되는 형태로 보인다.  
- **도구 사용 권한:** Claude Code는 로컬 코드를 실행하거나 명령어를 실행할 수 있도록 설계되었으며, 특정 명령어/파일 접근 권한 제어 기능이 존재할 가능성이 있다. 예를 들어 OpenAI Codex 기반 도구에서는 네트워크 차단이나 파일 액세스 제한이 있지만, Claude Code의 자세한 보안 설정은 공개되지 않았다.  
- **파일 수정:** Claude Code는 사용자가 업로드한 파일을 편집하거나 새 파일을 생성할 수 있는 코드 에디터 기능이 있다. 하위 에이전트가 파일을 수정하는 행위 자체는 이론적으로 가능하나, Claude Code가 여러 에이전트 간 파일 충돌을 자동 해결해주지는 않는다.  
- **터미널 명령 실행:** Claude Code는 셸 명령을 실행하여 파일을 컴파일하거나 테스트를 돌리는 기능을 지원하는 것으로 알려져 있다. 다만 이 때 어떤 명령을 허용/제한하는지는 공개되어 있지 않으므로, 위험한 명령은 기본적으로 비허용일 수 있다.  
- **결과 전달:** 세션 내에서 에이전트가 출력한 결과(예: 코드, 로그 등)는 동일 세션의 상위 에이전트가 볼 수 있다. 그러나 독립된 subagent가 생성된다면 이 결과를 자동으로 전달하는 기능은 제공되지 않는다. 결과 공유는 외부에서 API나 파일 시스템을 통해 구현해야 한다.  
- **병렬/순차 실행:** 단일 Claude Code 세션은 한 번에 하나의 발화와 응답으로 진행된다. 공식 지원으로 *동일 세션 안에서* 여러 에이전트를 병렬 호출하는 기능은 없다. 여러 에이전트를 동시 실행하려면 각각 별도 세션을 운영해야 하며, Claude Code 자체에서 병렬 제어는 지원하지 않는다.  
- **모니터링:** 에이전트의 실행 시간, 토큰 사용량 등의 메트릭은 Claude API나 콘솔에서 일부 확인 가능하지만, 이를 기반으로 자동 재시도/승격 로직을 제어하는 기능은 제공되지 않는다. 사용량 추적은 수동으로 모니터링하거나 외부 로깅 시스템이 필요하다.  
- **범위/권한 제한:** Claude Code 프로젝트별 설정 파일이나 에이전트 정의 파일이 공식적으로 존재하지 않는다. 작업 범위나 파일 접근 권한을 설정하는 기능 역시 공개된 바 없다. 기존에는 각 세션이 동일한 작업 디렉토리를 공유하나, 권한 격리는 사용자가 직접 관리해야 할 것으로 보인다.  
- **기타:** 공식 API 문서상 Claude Code에는 프로젝트 기반 연속 대화 기능(세션 persist)이 있으며, 각 세션은 입력 히스토리를 참고할 수 있다. 그러나 이력 공유는 세션 단위로 한정되며, 서로 다른 모델/세션 간 공유는 지원되지 않는다.  

> **요약:** Claude Code는 강력한 코드 편집 및 실행 환경을 제공하지만, 여러 모델/에이전트를 동시에 운용하거나 고급 workflow(작업 분할, 에이전트 간 통신, 자동 승격 등)를 구현하는 기능은 명시적으로 지원되지 않는다. 멀티에이전트 구조를 구성하려면 추가 도구와 개발이 필요하다.  

# 4. 모델별 역할 분배 가능성  
Claude Code나 유사한 AI 에이전트 플랫폼에서는 일반적으로 최상급(고성능) 모델과 저비용(경량) 모델을 용도에 맞게 조합하려는 시도가 있다. 예를 들어 **최상급 모델**은 복잡한 의사결정·검증·계획 수립에, **저비용 모델**은 단순 반복 작업이나 예비 검사에 각각 사용한다는 구상이다. 하지만 Claude Code 내부에서 *동일 세션 안에서* 모델을 바꾸거나 여러 모델을 자동으로 분배하는 기능은 현재 제공되지 않는다. 따라서 다음과 같이 분리해서 고려해야 한다.

- **모델 전환:** 현재 Claude Code 세션은 생성 시점의 모델에 고정된다. 따라서 한 작업 흐름에서 다른 모델로 전환하려면 별도 세션을 생성해야 한다. 예를 들어, 계획 단계에서는 Claude-Opus를, 코딩 단계에서는 Claude-+ 같은 모델을 사용하는 식으로 나눌 수 있지만, 이를 자동화하려면 별도 스크립트 또는 오케스트레이터가 필요하다.  
- **서브세션별 모델 지정:** Anthropic API에서는 호출 시 모델명을 지정할 수 있으며, 이를 사용해 역할별로 모델을 다르게 설정할 수 있다. 즉, 스크립트를 통해 각 작업(task)마다 적합한 모델을 호출하는 방식으로 구현할 수 있지만, Claude Code 인터페이스 자체에 모델 지정 기능은 없다. 오직 API나 외부 툴을 통해 다르게 지정해야 한다.  
- **작업 난이도 기반 라우팅:** 아이디어에 맞춰 “저난이도 작업은 Claude-더 저렴한 모델, 고난이도는 더 강력한 모델”로 라우팅할 수 있다. 예를 들어, 단순 텍스트 검색이나 루틴한 코드 수정은 GPT-3.5·Claude-Access 같은 경량 모델로, 복잡한 알고리즘 구현이나 버그 수정은 GPT-4·Claude-Advanced 같은 고성능 모델로 처리하도록 설계할 수 있다. 현재 공개 자료상 자동 라우팅 기능은 없으므로, 난이도 분류와 모델 선택 로직은 외부에서 구현해야 한다.  
- **모델 간 실패 전환:** 특정 모델이 실패했을 때 상위 모델로 재호출하는 자동 전환 메커니즘은 Claude Code에 내장되어 있지 않다. 이를 위해서는 “만약 A 모델이 실패하면 B 모델을 호출하라”는 조건부 로직을 추가로 작성해야 하며, Claude Code 자체는 실패를 인지해 자동으로 다른 세션을 불러주지 않는다.  
- **대화 문맥 공유:** 한 모델에서 생성된 입력/출력(context)을 다른 모델로 넘기는 기능은 제공되지 않는다. 즉, 관리자가 코딩 모델과 검증 모델을 각각 사용한다면, 작업 내용을 다음 모델에게 전달하려면 직접 텍스트나 파일로 옮겨야 한다. Anthropic API 자체는 context를 전달 가능하지만 별도 세션에서는 다시 넘겨줘야 하므로 수동 프로세스다.  
- **구독 vs API 방식:** Claude Code 자체(IDE로서의 인터페이스)와 API를 통한 접근은 일부 기능에 차이가 있을 수 있다. 예를 들어, IDE에서는 편리한 코드 편집 기능이 제공되지만 모델 호출 로그나 토큰 사용량 모니터링은 제한적일 수 있다. 반면 API 사용 시 개발자가 직접 필요 기능을 구현해야 하지만, 세션별 모델/매개변수 지정과 비용 추적은 상대적으로 자유롭다. 기능 차이는 공식 문서에 명시적 비교가 없으나, 일반적으로 IDE에서는 사용자 친화적인 UI에 중점, API에서는 기술적 제어에 중점이다.  

> **요약:** Claude Code 내에서 모델별 역할 분배는 *기본 기능*으로는 지원되지 않으며, 다양한 모델을 역할별로 배치하려면 외부 오케스트레이션이 필요하다. API로 여러 세션을 생성하고 각 세션에 다른 모델을 지정하는 방식으로 구현할 수 있으나, 이는 수동 설계가 필요하다. 자동 라우팅·전환은 현재 제공되지 않고 개발자 몫이다.  

# 5. 실패 감지와 에스컬레이션 구조  
멀티에이전트 시스템에서 하위 모델(작업 에이전트)의 실패를 감지하고 상위(또는 다른) 모델이 개입하는 구조는 필수적이다. Claude Code와 관련 에코시스템에서 가능한 실패 유형과 감지/처리 방안을 다음과 같이 조사했다.  

## 5.1 실패 유형  
1. **코드 비실행 오류:** 작성된 코드가 실행되지 않거나 컴파일/런타임 오류를 냄.  
2. **테스트 실패:** 작성한 코드가 단위/통합 테스트를 통과하지 못함.  
3. **반복 오류:** 동일한 버그나 오류가 여러 번 동일한 방식으로 발생함(모델이 똑같은 잘못을 반복).  
4. **수정 반복:** 모델이 동일한 수정을 반복 제안하며 개선이 없음(수렴되지 않음).  
5. **요구사항 미충족:** 산출물이 원래 요구사항을 만족하지 못하거나 누락된 기능이 있음.  
6. **잘못된 파일 수정:** 의도한 파일이 아닌 다른 파일을 수정하거나, 경로를 잘못 지정함.  
7. **가짜 완료 보고:** 모델이 작업 완료를 보고했으나 실제로 실행 결과나 기능이 완성되지 않음.  
8. **장시간/무한 반복:** 작업(코드 실행, 테스트 등)이 너무 오래 걸리거나 무한 루프에 빠짐.  
9. **의존성 설치 실패:** 필수 라이브러리나 패키지 설치에 실패함.  
10. **권한 부족:** 파일 쓰기, 네트워크 접근, 시스템 명령 실행 권한이 없어 실패함.  
11. **충돌:** 다른 모델이나 프로세스가 같은 파일을 수정하여 Git 충돌 등이 발생.  
12. **잘못된 원인 파악:** 모델이 문제를 잘못 진단하여 엉뚱한 수정 시도.  
13. **불확실성 낮음:** 모델의 confidence가 낮거나 명확한 결과를 내놓지 못함(Claude Code 자체는 수치화된 confidence 제공 안 함).  

## 5.2 실패 감지 방법  
- **테스트 결과 자동 확인:** 자동화된 테스트(단위/통합 테스트 스크립트)를 실행하여 합격/불합격을 판단할 수 있다. Claude Code 환경에서 테스트를 실행해 패스/페일 메시지를 잡으면 실패 여부 확인이 가능하다.  
- **종료 코드 확인:** 쉘 명령(컴파일, 실행, 스크립트)의 exit code를 점검하여 0이 아니면 실패로 간주할 수 있다. Claude Code에서 터미널 명령을 실행할 때 반환값을 확인하는 스크립트를 추가하면 활용할 수 있다.  
- **로그 분석:** 에러 로그나 출력 메세지를 파싱하여 오류 패턴(예: `Exception`, `Error`, `Traceback`)을 찾는 방식. 예를 들어, Python 실행 중에 `Error:`가 출력되면 실패로 분류한다. Claude Code가 로그를 JSON으로 주는지 여부는 명시되지 않았으나, 콘솔 출력 텍스트는 분석 가능하다.  
- **파일 변화 비교:** Git diff 등을 이용해 코드 변경 결과를 비교하여 예상치 않은 변경이 있는지 확인한다. 예를 들어, 모델이 잘못된 파일을 수정하거나 이상한 변경을 했는지 알 수 있다. 이를 위해서는 외부에서 Git 워크플로우를 관리하며 커밋 전후를 검토해야 한다.  
- **정적 분석:** 코드 스타일체크, lint, type 검사 등을 통해 코드 오류(예: 타이핑 오류, 코드 표준 위반)를 사전에 잡는다. Claude Code 자체에 lint 기능이 내장돼 있는지 확인되지 않았지만, 외부 툴과 연계하면 가능하다.  
- **테스트 통과 여부:** 실제 동작 테스트(유닛테스트/통합테스트)를 통해 비즈니스 로직 오류를 검출한다. 테스트를 자체 루틴으로 돌려보고 결과를 토대로 성공/실패를 판단한다.  
- **요구사항 체크리스트:** 작업 시작 시 요구사항을 정의해두고, 완료 시점에 체크리스트를 사용하여 목표 달성 여부를 검사한다. 예: “문서화된 모든 기능이 구현되었는가?” 등. 이는 사람이 만든 검증 프로세스를 모델에게 물어보는 방법.  
- **별도 검증 모델:** 다른 모델 또는 Agent를 사용해 결과를 검증하도록 한다. 예를 들어, 코드 결과를 다른 Claude나 GPT에게 읽게 해보고 “이 코드가 요구사항을 충족하는가?”라고 물어보는 식이다. 다만 Claude Code에서는 동일 세션에서 이런 검증 에이전트를 호출하는 기능은 없으므로, 별도 세션 또는 오케스트레이터를 통해 구현해야 한다.  
- **오류 반복 감지:** 동일한 오류 로그나 예외가 반복될 경우, 모델이 같은 실수를 계속한다고 판단할 수 있다. 예를 들어, 세 번 연속 `NameError`가 발생하면 해결하지 못하는 것으로 판단하고 재접근한다. 이를 위해서는 실패 기록을 추적하는 로직(예: Redis, DB)에 의존해야 한다.  
- **시간/토큰 제한:** 정해진 시간이나 토큰 사용량을 초과하면 작업을 중단하고 실패로 간주하는 방법. Claude Code는 자체 타임아웃을 설정할 수 있지만 자동 escalation 규칙은 제공되지 않는다. 개발자가 직접 타이머를 적용해야 한다.  
- **구조화된 리포트:** 에이전트에게 결과를 JSON 등 구조화된 포맷으로 출력하게 한 뒤, 특정 필드를 보고 성공/실패를 판단한다. 예를 들어, 모델이 `"success": true/false` 값을 반환하도록 지정할 수 있다. Claude Code는 기본적으로 자유 텍스트를 쓰므로, 명시적인 지시(prompt)로 구현해야 한다.  
- **관리자 재검토:** 최상급 에이전트(또는 사람)가 최종 결과를 살펴보고 “이게 올바르게 수행되었는가?”를 판단한다. 이는 최후 단계의 수동 검증이며, 자동화가 어려운 경우 인간 개입이 필수적이다.  
  
> **감지 요약:** 테스트 실행 및 종료 코드 확인은 실용적인 기본 실패 감지 방법이다. 로그 및 git 비교, 정적 분석 등은 보조적 수단으로 사용할 수 있다. Claude Code에 내장된 자동 체커는 없으므로, 모든 판단 로직은 외부에서 구현하거나 모델에게 맡겨야 한다.  

## 5.3 Escalation 단계  
여러 모델을 활용한 단계별 에스컬레이션(승격) 구조는 자동화 효율과 비용 절약을 위해 흔히 제안된다. Claude Code 에코시스템에서 다음 단계를 어떻게 구현할 수 있는지 살펴본다.  

1. **1단계: 저비용 모델 작업 수행** – 간단한 문제는 저비용(경량) 모델(예: Claude Cumulative, GPT-3.5 계열)에게 맡긴다. 여기서 해결 가능하면 고비용 모델 호출을 피할 수 있다.  
2. **2단계: 자동 테스트/검증** – 작업 결과를 자동 테스트하거나 검증 수단(스크립트, 정적 검사)으로 점검한다. 만약 테스트를 통과하지 못하면 실패로 분류한다.  
3. **3단계: 동일 모델 재시도** – 저비용 모델이 실패하면 다른 지시(prompt)나 추가 정보로 *같은 모델*을 재시도하게 한다. 예를 들어, “이전 답변에서 무엇이 잘못되었는지 찾아서 수정해”와 같은 추가 프롬프트로 다시 시도한다. 재시도 횟수(예: 최대 2회)도 정해둔다.  
4. **4단계: 다른 하위 모델로 교체** – 그래도 해결되지 않으면 동일 급의 다른 모델로 교체한다. 예를 들어, Claude Cumulative 대신 Claude Secure를 사용하거나 GPT-3.5-turbo 대신 GPT-4 모델로 시도한다. Claude Code 자체에서 모델 전환은 지원되지 않으므로, 외부에서 다른 API 키로 호출하거나 다른 세션을 운영해야 한다.  
5. **5단계: 중간급 모델 분석** – 여전히 실패하면 중급(또는 고급) 모델(예: GPT-4, Claude Advanced)에게 원인을 진단하도록 맡긴다. 이 모델은 “왜 실패했는지 분석하라”는 지시를 받아 문제 원인을 설명하고, 추가 정보를 수집한다. Claude Code에 동일 프롬프트 연속 실행 기능이 없다면, 재구성된 프롬프트를 새 세션에서 사용해야 한다.  
6. **6단계: 최상급 모델 개입** – 문제가 복잡하거나 크리티컬하다고 판단되면 최상급 모델(예: GPT-4o, Claude Max)에게 직접 작업을 맡긴다. 이때 모든 이전 결과(코드, 로그, 에러 메시지 등)를 제공해 모델이 상황을 파악하게 한다. Claude Code 세션에서는 이 데이터를 텍스트로 제공하거나 링크로 첨부해야 한다.  
7. **7단계: 사용자에게 보고** – 최후 단계로, 인간 개발자에게 알림 또는 검토를 요청한다. 예를 들어, 실패 상세 로그와 함께 PR을 생성하거나 이메일 알림을 보내 최종 결정을 받는다. Claude Code의 경우, 사람이 들어와서 채팅할 수 있지만 완전 자동화된 보고 시스템은 구현해야 한다.  

각 단계의 **자동 전환 조건**과 **수동 개입 기준**은 별도 로직으로 구현해야 한다. 예를 들어, 특정 에러 코드 발생 시 자동으로 3단계로 넘어가고, 최상급 모델이 세 번 실패하면 사용자 개입하라는 식으로 설정할 수 있다. Claude Code는 자체적으로 스텝 전환 규칙을 제공하지 않으므로, 슬랙 알람, GitHub Action, 서버리스 함수 등의 외부 이벤트 트리거로 구현하는 방식을 고려해야 한다.  

> **에스컬레이션 요약:** 실제로 단계적 승격 구조를 만들기 위해서는 Claude Code 외부의 제어 로직이 필요하며, 각 단계의 조건(예: 테스트 실패, 재시도 횟수)을 명확히 정의해야 한다. Claude Code 내부 기능만으로는 자동단계를 관리할 수 없으므로, 개발자가 직접 흐름을 짜야 한다.  

# 6. 구현 방법과 도구 조사  
Claude Code 기반 멀티에이전트 시스템 구축에는 공식 생태계 도구와 오픈소스 프레임워크·인프라가 모두 활용될 수 있다. 필요한 구성 요소와 역할을 정리한다.  

## 6.1 Anthropic 공식 생태계  
- **Claude Code (IDE/API):** Anthropic의 통합 개발환경. 코드 편집, 실행, 로그 확인 등의 기능을 제공. *현재 세션당 하나의 모델*만 실행 가능하며 외부 API 호출도 지원한다. 이외에 명시적 subagent 기능은 없다.  
- **Claude Agent SDK / API:** Anthropic에서 제공하는 SDK(예: Python 라이브러리)와 HTTP API. Claude 모델을 호출하여 프로그래밍적으로 작업할 수 있다. API를 통해 여러 세션을 생성, 메시지를 주고받는 방식으로 멀티에이전트 동작을 에뮬레이션할 수 있다. 예를 들어, Python으로 코딩하여 필요할 때마다 다른 모델을 호출하는 방식이다.  
- **MCP (Multi-Channel Projects):** Anthropic 문서에 명시된 바는 없지만, MCP는 Claude 프로젝트 관리 툴 또는 API인 것으로 추측되며, 멀티 프로젝트/세션 관리를 위한 기능을 제공할 수 있다. 명칭만으로 판단하자면, 여러 채팅 세션을 동시에 관리할 수 있는 컨테이너 역할일 수 있지만, 공식 문서 확인이 필요하다.  
- **Hooks / Commands / Skills:** Claude Code 또는 Anthropic 플랫폼에서 명령어를 실행하거나 외부 도구를 호출하는 기능. 예를 들어, ChatGPT의 ‘코드 인터프리터’나 ‘Tools’와 유사할 수 있다. 공식 문서에 Claude용 hooks이나 commands 시스템은 언급되지 않으나, 내장된 파이썬 REPL이나 쉘 기능을 통해 실행 명령이 가능. 그렇지만 권한 제어나 특정 커맨드 제한 기능은 확인되지 않아, 일반 사용자는 위험한 명령 실행에 주의해야 한다.  
- **세션 및 컨텍스트 관리:** Claude Code 세션은 대화 히스토리를 메모리로 관리하며, 프로젝트 단위로 여러 파일을 포함할 수 있다. API 사용 시에는 별도 컨텍스트 저장소(DB)가 필요하며, 상태는 직접 관리해야 한다. 즉, 세션간 컨텍스트를 공유하거나 백업하는 공식 기능은 없다.  
- **작업 로그/결과 관리:** Claude Code 콘솔은 실행 결과와 로그를 출력하지만, 이를 자동으로 저장하는 기능은 없다. 개발자는 API 응답을 받아 로컬 로그 파일에 기록하거나, 외부 서비스(예: Amazon S3, 로깅 서버)로 전송하여 보관해야 한다.  

> **요약:** Anthropic에서 제공하는 공식 도구는 Claude 모델 호출과 코드 실행을 지원하지만, 다중 에이전트 협업에 필요한 워크플로우 관리 기능은 제한적이다. 멀티에이전트나 workflow orchestration을 위해서는 외부 라이브러리나 스크립트를 활용해야 한다.  

## 6.2 오픈소스 멀티에이전트 프레임워크  
아래 프레임워크들은 AI 에이전트를 조합하거나 멀티모델 환경을 구축하는 데 활용할 수 있다. Claude Code와 직접 연동 여부는 각 라이브러리의 모델 지원 내용을 확인해야 한다.  

- **LangChain:** LLM 체인을 구성하는 Python 라이브러리. 다양한 LLM을 연결하고, memory, retriever, Agents 등의 컴포넌트를 제공. 에이전트를 직접 지원하며, 서로 다른 모델로 역할 분담이 가능하다. 예를 들어 LangChain Agent를 사용하면 하나의 ‘Master’ 역할이 있고, 작업마다 다른 LLM을 호출하도록 스크립트를 설계할 수 있다. Claude를 직접 지원하지는 않지만, OpenAI나 Hugging Face의 Claude-like 모델을 활용할 수 있다. 재사용 커뮤니티가 크고, MIT 라이선스.  
- **LangGraph:** 언어 에이전트를 플로우 그래프로 연결하는 프레임워크. 노션(No)브랜드로 개발되었으며, 다중 단계 작업을 정의하고 실행할 수 있다. 커스텀 작업(노드)을 만들어 각기 다른 LLM API를 호출할 수 있어, 멀티에이전트를 구성하는 데 유용하다. 다만 활동성이 LangChain에 비해 낮은 편이다.  
- **AutoGen:** 메타에서 공개한 멀티에이전트 프레임워크. 사용자와 봇, 봇과 봇 간의 대화 시나리오를 정의할 수 있다. 예를 들어, “Plan Agent”와 “Worker Agent”를 정의해 서로 역할을 나눌 수 있으며, 코드 작업 예제도 일부 제공한다. Claude 모델과의 직접 호환 여부는 확인이 필요하나, GPT-4 등 다양한 LLM을 지원. 한글 문서나 지원은 미흡하나, 실험적인 구현 가능성을 제공한다.  
- **MetaGPT:** Microsoft 연구진이 공개한 협업용 멀티에이전트 시스템. 소프트웨어 개발을 타깃으로 만든 툴로, 요구 분석부터 테스트까지 여러 에이전트가 협업한다. 예를 들어 한 에이전트가 설계를 하고, 다른 에이전트가 코딩, 또 다른 검증 에이전트가 리뷰하는 시나리오다. 실제로 GitHub 저장소와 연동해 코드 생성을 자동화할 수 있으며, 태스크별 에이전트를 커스텀할 수 있다. 다만 라이선스는 MIT이고, 유지보수는 활발치 않다.  
- **OpenHands, SWE-agent, CrewAI 등:** 기타 연구 커뮤니티나 스타트업에서 나온 에이전트 프레임워크들. 예를 들어 SWE-Agent는 테슬라 출신 개발자가 만든 프로젝트로, 소프트웨어 엔지니어링 과업을 자동화한다. OpenHands는 다수 에이전트 간 협업 워크플로우를 지원한다. 각각 특화된 도메인이 있고, Claude 지원 여부는 개별 확인이 필요하다. 최근 트렌드는 LLM orchestration 플랫폼(LlamaIndex, Fedora)의 등장도 있어, 이 분야는 빠르게 발전 중이다.  

> **요약:** LangChain과 MetaGPT는 멀티에이전트 워크플로우 구축에 많이 사용되는 오픈소스 도구다. 이를 이용하면 Claude Code 세션을 에이전트로 감싸거나, Claude API와 연동하여 역할 분배, 상태 저장, 실패 재시도 등을 자동화할 수 있다. 그러나 모든 프레임워크가 Claude를 네이티브로 지원하는 것은 아니므로, API 적응 계층(클라이언트)를 구현해야 한다.  

## 6.3 실행 및 오케스트레이션 인프라  
실제 서비스 수준 시스템으로 구현할 때는 다음과 같은 기술이 사용된다. 각 기술은 필요한 상황에 맞춰 사용해야 한다.  

- **Python/Node.js:** 백엔드 로직(오케스트레이터, 워크플로우 제어)을 구현하는 언어. 대부분 Python 생태계(LLM 라이브러리, LangChain 등) 위주지만, 필요 시 Node.js(LangChainJS 등)를 사용할 수 있다.  
- **FastAPI (또는 Flask/Django):** 에이전트를 REST API로 감싸거나, 워크플로우 컨트롤러를 구축할 때 사용. Claude API 호출을 묶거나 프론트엔드 대시보드를 만드는 데 유용하다. 예: “/plan”, “/work” 같은 엔드포인트를 두고 JSON으로 태스크 전달.  
- **Docker:** 에이전트나 서비스 컨테이너화. 각 역할(agent)을 독립 컨테이너로 띄워 버전, 의존성을 격리할 수 있다. Claude Code 자체는 클라우드 서비스이지만, 커스텀 오케스트레이터는 도커 컨테이너로 운영하는 것이 일반적이다.  
- **Redis/Message Queue (RabbitMQ, Kafka):** 에이전트들 간 메시징 혹은 작업 대기열 관리. 예를 들어, Manager가 작업을 분해해 Redis 큐에 넣으면 Worker들이 가져가서 처리하도록 한다. 작업 상태 추적, 재시도 로직 구현에도 사용된다.  
- **PostgreSQL/SQLite:** 상태 저장, 결과 기록용 데이터베이스. 에이전트 결과와 로그, 태스크 트래킹 등을 저장한다. SQLite는 소규모나 데모용, 대규모 서비스엔 PostgreSQL 같은 DBMS를 사용한다.  
- **Celery/Ray:** 분산 작업 스케줄링 라이브러리. Celery는 주로 비동기 태스크 큐로, Ray는 LLM과 분산 컴퓨팅에 특화된 라이브러리로 멀티에이전트 실행을 지원한다. 대규모로 에이전트를 동시에 실행하거나 워크플로우를 관리할 때 유용하다.  
- **Kubernetes:** 컨테이너 오케스트레이션. 다수의 에이전트를 안정적으로 운영하고 자동 확장, 재시작, 로드 밸런싱 등을 수행할 때 사용한다. 소규모에선 필요하지 않지만, 대규모 서비스를 염두에 둔다면 고려할 수 있다.  
- **Git (Worktree, Branch):** 멀티에이전트가 동시에 파일 작업을 할 경우, Git 워크스페이스를 분리해서 작업해야 한다. `git worktree`로 복수의 작업 디렉토리를 만들어 각 워커가 별도 브랜치에서 작업하도록 하면 충돌을 줄일 수 있다. 작업 완료 후 통합(merge, PR)도 Git을 통해 이뤄진다.  
- **CI/CD & GitHub Actions:** 자동화된 빌드/테스트 파이프라인. 각 모델이 만든 코드를 검증하고 병합하기 위해 CI(예: GitHub Actions, Jenkins)를 사용한다. 예를 들어, 에이전트가 PR을 만들면 Actions가 자동으로 테스트 스크립트를 돌린다.  
- **테스트 러너(예: pytest), 로깅, 모니터링:** 코드 작성·수정 결과의 품질을 검증하고 시스템 상태를 점검하기 위해 필요하다. 로깅 라이브러리(ELK 스택, Sentry 등)를 사용해 에이전트 실행 로그를 모니터링하고, 알림을 설정한다.  

> **요약:** 멀티에이전트 시스템에는 다양한 일반적인 백엔드/DevOps 기술이 사용된다. Claude Code 자체는 클라우드 서비스지만, 외부 오케스트레이션 및 실행 환경을 구축할 때 위 도구들이 활용된다. 특히 작업 간 파일 조율을 위해 Git 워크플로우와 CI/CD는 필수적인 인프라로 여겨진다.  

# 7. 코드 작업 예시: Flutter 앱 개발  
예시: **“Flutter 앱에 새 기능 추가 및 서버 API 연동, 테스트·오류 수정까지 자동화”** 시나리오를 고려해보자. 가능한 멀티에이전트 구조와 도구를 상정하여 분석한다.  

- **파일 공유:** Claude Code 세션 자체가 독립된 파일 시스템을 사용하기 때문에, 여러 세션이 동일한 저장소를 *즉시* 공유하진 않는다. 이를 해결하려면 버전 제어(Git) 기반으로 동기화해야 한다. 예를 들어, 각 에이전트는 특정 브랜치에 작업한 뒤 마스터 브랜치로 Merge 요청을 한다. Claude Code에서 Git 명령을 사용할 수 있다면 해당 브랜치로 체크아웃/커밋/푸시 작업을 명령으로 자동화할 수 있다.  
- **작업 공간 분리:** `git worktree`를 통해 프로젝트의 서로 다른 디렉토리를 만들어놓으면, 여러 에이전트가 동시에 작업해도 로컬 파일 시스템 수준에서 충돌이 발생하지 않는다. 예를 들어 Agent A는 `feature/ui`, Agent B는 `feature/api` 워크트리에 붙어서 작업한 뒤, 마지막에 `master`로 병합할 수 있다. 이 방식은 Claude Code IDE 환경에서 자동으로 지원되지 않으므로, 에이전트에게 워크플로우를 알려주거나 외부 스크립트가 명령해야 한다.  
- **결과 검토:** 한 모델의 코드 산출물을 다른 모델이나 관리자 모델이 검토하려면, 결과를 명확히 공유해야 한다. Claude Code에서는 모델이 작업한 코드를 텍스트로 챗에 보내거나 파일에 저장하게 한 뒤, 검토할 다른 에이전트에게 전달한다. 예를 들어, Agent A가 생성한 Dart 코드 스니펫을 메시지로 받고 Agent E(코드 리뷰)가 그 내용을 검사하게 할 수 있다. 이때 코드 전체를 보낼 수 있으나, 긴 코드라면 Git 링크나 요약을 사용해야 한다. 현재 Claude Code에 내장된 전체 파일 공유 기능은 없기 때문에, 외부 리포지토리와 연동하는 방법이 효과적이다.  
- **모델 전용 작업:** 테스트 작성 모델과 코드 작성 모델을 분리하려면, 각 에이전트에게 명확한 역할을 부여한다. 예를 들어, Agent C는 API 연동을 전담하고, Agent D는 테스트 코드 작성을 전담하도록 프로프트를 달리한다. Claude Code에 역할별 시스템 프롬프트 기능이 없으므로, 프롬프트나 초기 대화에서 역할을 설명해 주어야 한다. 에이전트 간 역할 명세가 분명할수록 작업 충돌이 줄어든다.  
- **Diff 및 로그:** 관리자(최상급 모델)는 git diff나 CI 테스트 결과를 보고 판단해야 한다. 예를 들어, Agent D가 작성한 테스트가 실패하면 관리자에게 결과 로그를 반환하게 하고, 관리자는 그 내용을 다시 한 번 큰 모델에 검토받는다. Claude Code는 기본적으로 Git diff 명령 결과를 바로 출력해주지는 않으므로, `git diff` 명령을 CLI 도구로 실행하도록 지시해야 한다.  
- **충돌 및 복구:** 만약 두 워커가 동시에 같은 파일을 수정하여 충돌이 발생하면, Git 충돌 해결 프로세스가 필요하다. 이는 자동화하기 어렵고, 보통 인간 개발자 개입을 권한다. 에이전트끼리 미리 브랜치로 분리 작업을 하면 충돌은 줄이지만, 만약 생기면 `git merge` 시 에러가 나고, 관리자가 수동으로 해결해야 한다. 시스템 관점에서는 “병합 실패” 로그를 감지하여 관리자에게 알려주는 식으로 처리가 가능하다.  
- **인간 개입 시점:** 주로 최종 병합 전 리뷰 단계에서 인간의 확인이 필요하다. 예를 들어, 모든 테스트가 통과해도 새로운 기능의 비즈니스 로직이 실제 요구사항과 일치하는지는 사람이 최종 검토해야 한다. Claude Code는 사용자 승인을 위한 UI를 제공하지 않으므로, PR 리뷰나 메시징 도구(슬랙, 이메일)를 통해 알림을 보내야 한다.  

> **요약:** 실제 코딩 작업에서는 Claude Code만으로는 에이전트 간 협업이 완전히 자동화되기 어렵다. 파일 공유와 충돌 관리를 위해 Git 기반 워크플로우가 필요하며, 에이전트별로 작업 공간을 분리해야 한다. 각 모델의 출력물을 다른 모델이 리뷰하도록 할 때는 명시적 전달(코드 스니펫 전송 등)이 필수다. 또한, 충돌 해결이나 최종 검증 등에는 여전히 사람의 개입이 요구된다.  

# 8. 모델 선택 및 비용 최적화  
서로 다른 모델을 조합할 때 비용과 성능 측면에서 구조별 비교가 필요하다. 여기서는 5가지 구조를 가정하고 각 장단점을 간단히 살펴본다. 실제 수치는 Claude/클라우드 요금표나 GPT 가격을 참고해야 한다.

- **구조 1: 모든 작업을 최상급 모델 하나가 수행**  
  - **비용:** 매우 높다. (예: GPT-4o 호출 횟수가 많을수록 비용 폭증).  
  - **속도:** 작업마다 큰 모델을 호출하므로 응답 지연(레이턴시) 증가.  
  - **품질:** 일반적으로 최고. 하나의 강력한 모델이 전과정을 처리하므로 컨텍스트 손실이 적고, 일관성 높은 결과 가능.  
  - **장점:** 구현이 가장 단순하며, 에이전트 간 통신 없이 한 모델로 끝냄.  
  - **단점:** 비용·시간 효율이 매우 낮음. 작업이 복잡할수록 오버헤드 커짐. 작은 작업에 큰 모델을 쓰는 낭비가 많음.  

- **구조 2: 모든 작업을 저비용 모델이 수행**  
  - **비용:** 매우 저렴. (예: GPT-3.5 또는 Claude-Access 등)  
  - **속도:** 빠름. 간단한 모델 호출은 레이턴시가 짧다.  
  - **품질:** 낮음. 중요한 로직이나 정확도가 필요한 작업에서 실패 가능성 높음.  
  - **장점:** 비용 최저, 부하 분산 용이. 대량 작업이나 단순 반복 작업에 적합.  
  - **단점:** 버그/오류 재시도가 잦아져 전체 퍼포먼스가 떨어지고, 잘못된 결과 가능성이 크다.  

- **구조 3: 저비용 모델 수행 + 최상급 모델 검증**  
  - **비용:** 중간. 주로 저비용 모델을 쓰고, 결과 확인에만 고성능 모델 호출.  
  - **속도:** 검증 단계 추가로 지연. 그러나 코드 작성 등 많은 부분은 빠른 모델로 처리.  
  - **품질:** 저비용 모델이 제안하고 고급 모델이 리뷰를 한다. 오류를 발견하면 재작업할 수 있어 높은 신뢰도 가능.  
  - **장점:** 양쪽 장점을 취함. 초반 작업 비용 절약, 결과 품질은 큰 모델이 보증.  
  - **단점:** 검증 과정이 자동화되지 않으면 오히려 수고가 늘어나고, 고성능 모델 호출이 누적되면 비용 절감 효과가 줄어든다.  

- **구조 4: 저비용 모델 수행, 실패 시 최상급 모델 개입**  
  - **비용:** 저비용 모델로 대부분 처리하여 구조 3보다 더 절감 가능. 단, 실패가 잦으면 높은 모델 호출이 추가된다.  
  - **속도:** 실패 시 최상급 모델 대기 시간이 추가되어 변동적. 성공적인 태스크는 빠름.  
  - **품질:** 문제 해결에 실패한 일부 작업만 고급 모델로 넘기기 때문에 적절히 오류를 잡아낼 수 있다. 단, 실패 판단이 명확해야 한다.  
  - **장점:** 필요할 때만 고성능 모델을 사용하므로 비용 효율적. 실패할 만큼 복잡한 업무를 선별하여 처리.  
  - **단점:** 실패 판단 기준 설정이 어렵고, 잘못 판단하면 품질 저하. 반복 재시도가 많으면 오히려 비효율적일 수 있다.  

- **구조 5: 관리자(고성능) + 다수 하위(저비용) + 관리자 검증**  
  - **비용:** 중간. 관리자 모델 호출은 관리 역할 및 최종 검증에 한정하고, 대부분 작업은 저비용 모델이 수행.  
  - **속도:** 병렬 하위 모델 덕분에 처리 속도는 구조 1~3보다 빠를 수 있다. 관리자 개입은 병목이 될 수 있다.  
  - **품질:** 높은 수준. 관리자가 최종 승인 및 오류 처리를 하기 때문에 일관성이 높고, 병렬로 많은 작업을 처리할 수 있음.  
  - **장점:** 모듈화된 구성으로 유지보수가 쉽고, 오류가 발생해도 관리자가 바로 대응 가능. 작동 효율도 좋음.  
  - **단점:** 구현 복잡도가 매우 높다. 멀티세션 관리, 동기화 문제, 충돌 방지 로직 등 많은 추가 개발 필요. 비용과 레이턴시도 중간 수준.  

> **정리:** 비용 대비 성능 최적화를 위해서는 **구조 3~5** 형태가 유망하다. 특히 **구조 4**(저비용 작업 + 실패 시 고성능 개입)는 비용을 크게 절감하면서도 심각한 오류는 막을 수 있는 실용적인 트레이드오프이다. **구조 5**(관리자+작업자+검증자)는 이상적이나 복잡도와 개발 리소스가 많이 든다. 최종 설계는 작업 특성(난이도, 응답 시간 요구, 오류 허용도)과 비용 한도에 따라 선택해야 한다.  

# 9. 보안과 권한 관리  
여러 모델이 코드와 시스템 리소스에 접근할 경우 다양한 보안 리스크가 발생할 수 있다. Claude Code 자체의 보안 기능과 외부에서 신경 써야 할 사항을 구분하여 정리한다.  

- **파일 접근 권한 제한:** Claude Code 세션이 기본적으로 프로젝트 폴더 내 파일에 접근할 수 있다. 다수 세션 간 권한 격리는 없으므로, 멀티 에이전트 환경에서는 **컨테이너 격리**(Docker, VM)나 **사용자 계정 분리**가 필요하다. 예를 들어, 각 에이전트를 별도 Docker 컨테이너로 띄우고 파일시스템을 분리하여 악성 코드를 다른 에이전트가 건드리지 못하게 한다. Claude Code 내에서는 아직 사용자별 파일 권한 설정 기능이 공개되지 않았다.  
- **터미널 명령 제어:** Claude Code가 터미널 명령을 실행할 수 있다면, `rm -rf`, 네트워크 관련 명령 등 위험한 명령을 차단해야 한다. 공식 문서에는 특별히 금지된 명령 목록이 없으나, 안전을 위해 **네트워크 차단, 시스템 변경 불가** 방침을 두는 것이 좋다. 실제로 OpenAI의 코드 인터프리터는 인터넷 비활성화, 시스템 수정 제약 등 샌드박스 환경을 구축했다. Claude Code도 유사한 안전 조치를 가정해야 한다(예: `sudo` 권한 없음, 외부 통신 불가 등).  
- **환경 변수·API 키 보호:** 여러 모델이 통합 환경에서 구동될 때 중요 환경 변수나 비밀 키가 노출되지 않도록 주의해야 한다. Claude Code 프로젝트 설정에 API 키 등을 저장할 때 권한 분리를 명확히 하고, 에이전트마다 필요 최소한의 권한만 부여해야 한다. 예를 들어, Agent A에는 데이터베이스 읽기 키만, Agent B에는 쓰기 키만 주는 식이다.  
- **외부 네트워크 접근:** 에이전트가 인터넷에 함부로 접근하지 못하게 차단한다. Claude Code 인터페이스에서는 기본적으로 외부 웹 호출 기능이 제공되지 않을 것으로 예상되므로 [UNKNOWN], 만약 외부 API 호출이 필요하면 오케스트레이터 서버가 대신 처리하도록 한다.  
- **악성 코드 실행 방지:** AI에게 코드 수정을 시킬 때 악의적 코드(무한루프, 데이터 유출 시도 등)를 삽입할 가능성을 경계해야 한다. Claude Code의 자동검사 기능은 부족하므로, 코드 리뷰나 테스트 단계에서 발견해야 한다. 예를 들어, 모델이 생성한 스크립트에 문제가 없는지 `static analysis`나 “이 스크립트는 악성 동작을 포함하는가?” 같은 검증 과정을 추가할 수 있다.  
- **명령 검증:** 에이전트가 터미널 명령을 작성하거나 실행할 때, 명령 내용을 인간 또는 다른 모델이 사전에 검토하도록 한다. 위험한 명령(`rm`, `mkfs`, 비승인 포트 연결 등)이 있는지 체크하는 필터를 두는 것이 좋다. Claude Code 자체에 명령 가드가 있단 공식 언급은 없으므로, 래퍼 스크립트에서 명령어 화이트리스트/블랙리스트를 구현할 수 있다.  
- **관리자 vs 작업자 권한 차등화:** 관리자 모델과 작업 모델의 권한을 분리해야 한다. 예를 들어, 관리자만 코드 병합(PR 승인) 권한을 갖고, 작업자는 읽기/쓰기 권한까지만 갖도록 Git 브랜치 보호 정책을 둔다. Claude Code 내에는 역할 기반 권한 부여 기능이 명시되지 않으므로, Git 서버 설정이나 OS 권한으로 통제해야 한다.  
- **인간 승인 단계:** 중요한 배포나 민감한 작업은 전적으로 자동화하지 말고, 사용자 승인을 요구하는 메커니즘을 둬야 한다. 예: 새로운 기능 릴리즈 전 ‘인간 확인’ 태스크를 삽입한다. Claude Code 자체의 UI에서는 이를 지원하지 않으므로, 배포 파이프라인이나 채팅 알림 등을 이용해 승인 플로우를 설계한다.  
- **샌드박스:** Claude Code 실행 환경은 기본적으로 격리된 컨테이너 내에서 동작하도록 설계된 것으로 보인다. 그러나 다수 에이전트를 함께 운용하려면 Docker나 VM 샌드박스 등 물리적 격리를 강화해야 한다. 각 에이전트의 변경이 시스템에 영향을 미치지 않도록 고려해야 한다.  
- **데이터 손실/삭제 방지:** 실수로 중요한 파일이 삭제되지 않도록 백업 정책을 세운다. 예를 들어, 에이전트가 삭제 명령을 수행한 이력을 감시하고, 주요 파일은 Git으로 관리하며, 주기적으로 스냅샷을 만드는 식이다. Claude Code 자체에 복구 기능은 없으므로, 빌드된 인프라나 Git 커밋이 보호막 역할을 하게 한다.  
- **Prompt Injection:** 에이전트에게 사용자 입력(요청)이 포함된 prompt를 전달할 때, 악의적 코드나 지시문이 섞이지 않도록 데이터 클렌징이 필요하다. 예를 들어, 유저 쿼리가 `#### malicious_code ####` 형태로 에이전트에게 넘어가지 않도록 한다. Claude Code 자체에서 prompt 하위 시스템은 안전장치가 알려져 있지 않으므로, 사용자가 입력한 스크립트나 명령을 항상 검증하는 습관이 요구된다.  
- **로깅에 비밀정보 포함:** 에이전트 로그에 API 키, 비밀번호 등이 기록되지 않도록 주의한다. Claude API는 기본적으로 입력/출력 로그를 저장할 수 있지만, 민감정보는 마스킹 처리가 필요하다. 예를 들어, `os.environ['API_KEY']`를 출력하지 않도록 모델 프롬프트를 짜거나, 로깅 도구에서 필터링해야 한다.  

> **요약:** Claude Code 자체의 권한 제어 기능은 제한적이므로, 멀티에이전트 환경에서는 **컨테이너 격리, Git 정책, 실행 권한 제한** 같은 전통적인 보안 수단을 활용해야 한다. 특히 코드 실행 시 네트워크 및 시스템 명령을 제한하고, 모델이 만든 명령은 사전/사후 검증이 필수적이다. 사람이 승인하지 않은 상태로 무조건 실행해서는 안 된다.  

# 10. 기술적 한계와 위험 요소  
현재 공개된 자료와 커뮤니티 사례를 바탕으로, 제안된 시스템의 문제점과 한계를 정리한다.  

- **계획 오류:** 하위 모델이 상위 모델의 계획이나 명세를 잘못 해석하여 잘못된 코드를 작성할 수 있다. 예를 들어, “이 함수는 비동기식이어야 한다”는 요구를 “async 추가”로 오해할 수 있다. 이것은 Claude나 GPT 모두 발생하는 문제로, 관리자 모델의 재검토로 보완해야 한다.  
- **관리자 검증 실패:** 관리자 모델(또는 인간)이 하위 모델의 오류를 완벽히 찾아내지 못할 수도 있다. 예를 들어, 테스트 커버리지가 충분치 않으면 사각지대가 생겨 오류가 넘어갈 수 있다. 멀티에이전트에서도 “별도의 검증 단계”를 넣어도 100% 오류를 막을 수는 없다.  
- **오류 전파:** 여러 모델이 연쇄적으로 동작할 때, 하나의 잘못된 결과가 이후 단계로 계속 전파될 수 있다. 예를 들어, Agent A의 잘못된 API 응답이 Agent C의 디버깅을 잘못된 방향으로 이끌 수 있다. 서로 다른 모델이 격리된 환경에서 돌아도, 입력이 잘못되면 모든 downstream 에이전트가 영향을 받는다.  
- **동일 오류 반복:** 동일 모델을 여러 단계 사용하더라도 같은 오류를 반복할 수 있다. 예를 들어, 저비용 모델을 두 번 돌려도 비슷한 출력이 나온다면 하위 모델 그룹만으로 해결이 불가능하다. 모델 다양성을 충분히 확보하지 않으면 멀티에이전트의 이점이 줄어든다.  
- **컨텍스트 손실:** 여러 에이전트가 연속 대화를 한다면, 모든 정보를 이전 에이전트에게 넘겨주기 어렵다. Claude Code 세션 간에는 자동으로 대화 이력이 공유되지 않으므로, 이전 결과를 요약해서 넘겨주지 않으면 중요한 문맥이 누락된다. LLM은 긴 컨텍스트를 완벽하게 유지하지 못해, 교환되는 정보 일부가 잘려나갈 수 있다.  
- **상태 동기화:** 여러 워커가 병렬로 작업할 때 상태를 동기화하는 것이 어렵다. 예를 들어, Agent A가 파일을 업데이트할 때 Agent B도 같은 파일을 바탕으로 작업 중이면, 동기화가 안 돼 있던 B가 오래된 코드를 기반으로 움직일 수 있다. Git을 활용해 브랜치를 엄격히 관리하더라도, 병합 전 최신 상태 확인이 필요하다.  
- **파일 충돌:** 앞서 언급한 대로, 동일 파일의 충돌이 발생할 수 있다. 만약 자동 병합 정책을 잘못 설정하면 코드가 손상되거나 누락될 수 있다. 이 위험은 멀티에이전트 사용 시 내재적이므로, 충돌 감지/수동 해결 프로세스가 필수다.  
- **Race condition:** 두 명령이 거의 동시에 같은 리소스를 수정하려 할 때 발생한다. 예: 두 테스트 에이전트가 같은 데이터를 초기화하려고 하면 충돌 날 수 있다. 멀티스레드나 분산 시스템에서 흔히 발생하는 문제로, 이 역시 Git 수준 외에 작업 큐 락(lock)으로 제어해야 한다.  
- **무한 재시도:** 에스컬레이션 로직에서 실패 시 무한히 같은 모델을 재호출하게 되면, 비용 폭증 및 무한 루프에 빠질 수 있다. 예를 들어, 실패 조건이 모호하면 동일 모델이 계속 “나중에 해보겠다”만 반복할 수 있다. 최대 재시도 횟수와 타임아웃 설정이 필수다.  
- **비용 폭증:** 관리자가 너무 자주 개입하거나 모든 작업에서 최대 성능 모델을 호출하면 예상치 못한 비용이 발생할 수 있다. 비슷한 작업에 같은 모델을 계속 호출하면, 비용-효과를 의심해야 한다. 비용 상한(capping)이나 예산 모니터링도 함께 설계해야 한다.  
- **레이턴시 증가:** 멀티에이전트 구조는 관리·통신 오버헤드가 있어 단일 모델보다 지연이 커질 수 있다. 특히 병렬로 여러 모델을 호출하면 응답 대기가 길어질 수 있다. 사용자 경험 상 실시간 대화형이라면 응답 속도를 관리할 필요가 있다.  
- **작업 분담 오버헤드:** 여러 에이전트를 동원하려면 그만큼 프롬프트 작성, 결과 통합, 오류 처리 등 오버헤드가 생긴다. 단순 작업은 오히려 단일 모델로 처리하는 것이 빠를 수 있다. 즉, 멀티에이전트는 복잡도가 높아 작은 일에는 오버킬이 될 수 있다.  
- **관리자 과중:** 모든 작업을 CEO(관리자) 몫으로 만들면 관리자가 과부하될 수 있다. 예를 들어, 매 하위 결과마다 관리자에게 피드백을 요청하면, 관리자가 처리해야 하는 대화가 기하급수적으로 증가한다. 따라서 관리자 모델이 오직 핵심 판단에만 개입하도록 범위를 한정해야 한다.  
- **가짜 완료 보고:** 하위 모델이 “완료” 신호만 보내고 실제 수행 상태는 미완료인 경우. 예컨대, 스크립트 실행 없이 “성공”이라고 말하거나, 테스트를 건너뛰고 통과했다고 주장하는 경우가 있을 수 있다. 이런 거짓 보고를 막으려면 가능하면 실행 결과나 테스트 로그를 의무화해야 한다.  
- **다른 모델 간 충돌:** 예를 들어, 코드 스타일이나 아키텍처 설계에 대해 서로 다른 에이전트가 충돌할 수 있다. 한 에이전트가 Functional 패러다임을 추천했고, 다른 에이전트가 OOP 설계를 제안하면 최종 코드에 일관성이 떨어질 수 있다. 이를 방지하려면 스타일 가이드나 명시적인 규칙을 세워야 한다.  
- **권한 확대:** 멀티에이전트 시스템이 권한 상승을 일으킬 수 있다. 예를 들어, 관리자 에이전트가 사용자로서 하기 어려운 작업(외부 시스템에 접근 등)을 하도록 구성하면 보안 문제가 발생할 수 있다. 에이전트 별 권한을 최소한으로 제한해야 한다.  
- **판단과 실행 차이:** 모델이 제안하는 해결책과 실제 코드 실행 결과가 다를 수 있다. 예를 들어, 코드로 옮기면 실행 오류가 생기는데 모델은 이를 인지하지 못할 때가 있다. 따라서 항상 실행 가능한 코드로 변환되는지 최종 점검이 필요하다.  

> **요약:** 이론적 구상과 실제 구현 사이에는 많은 리스크가 존재한다. 멀티에이전트 환경에서는 오류가 복잡하게 얽혀 전파될 수 있고, 동기화나 충돌, 보안 이슈가 새로운 문제를 낳는다. 따라서 이러한 기술적 한계를 명확히 인식하고, 인위적인 제한 또는 추가 검증 메커니즘(휴먼체크, 철저한 자동화 테스트 등)으로 보완해야 한다.  

# 11. 구현 가능한 아키텍처 제안  
앞서 조사한 내용을 바탕으로, 현실적으로 구현 가능한 **3가지 아키텍처 예시**를 제시한다. 각 구조는 역할 분담 방식과 워크플로우가 다르며, 용도에 따라 장단점이 있다.  

## 아키텍처 A: 단일 관리자 + 다수 작업자 구조  
```
Manager
  ├─ Worker A (코딩)
  ├─ Worker B (테스트)
  ├─ Worker C (자료 조사)
  └─ Validator (검증)
```  
- **설명:** 관리자(고성능 모델)가 전체 워크플로우를 관리한다. 하위 에이전트들은 각각 역할(예: 코드 생성, 테스트, 문서화)을 수행하고, 완료 시 결과를 관리자에게 보고한다. 관리자는 이 결과를 종합하여 최종 결정을 내린다.  
- **작업 흐름:** Manager 에이전트가 작업을 분해하여 Worker에게 지시 → Workers가 독립 세션에서 작업 수행 → 결과(파일, 로그) 관리자에게 전달 → Validator나 Manager가 최종 검증.  
- **장점:** 직관적이고 역할 분담이 명확하다. 마스터 에이전트가 한눈에 상황을 파악할 수 있어 결과 통합이 쉽다. 에이전트별 전용 프롬프트를 설정하기 용이하다.  
- **단점:** Manager가 병목이 될 수 있다. 모든 결과를 한곳으로 모아야 하므로 중앙화된 컨트롤이 필요하다. 또한 Worker 간 데이터 종속성을 관리해야 한다. 예: Worker B가 Worker A의 코드가 필요하면, Manager가 먼저 코드 파일을 B에게 전달해야 한다. 구현 난이도가 있다.  
- **적합:** 작업이 비교적 명확하게 구분되고, 동시작업보다는 단계별로 이루어지는 프로젝트에 적합하다. 팀장-개발자 구조가 자연스러운 협업 시나리오.  
- **필요 기술:**  
  - Manager/Worker를 각각 Claude Code 세션 또는 API로 구성 (서브에이전트 기능은 없으므로 별도 세션 생성).  
  - 외부 오케스트레이터(LangChain, Celery 등)로 메시징/제어.  
  - Git 워크플로우로 파일 공유; 관리자 모델은 각 워커가 커밋한 브랜치를 병합 및 검토.  
  - 각 워커는 담당 브랜치에서 작업, 완료 시 PR 생성.  
  - Manager는 마지막에 병합하여 최종 점검(테스트 실행 및 리뷰).  

- **예제:** 프로젝트 관리 상황처럼, 관리자 모델이 Jira 티켓처럼 작업을 나눠주고, 개발자 에이전트가 구현하고 QA 에이전트가 검증하는 구조.  

## 아키텍처 B: 단계적 Escalation 구조  
```
저비용 모델 (단순 작업)
   ↓
중간급 모델 (분석/수정)
   ↓
최상급 모델 (완전 해결)
   ↓
인간 개입
```  
- **설명:** 작업을 한 번에 고성능 모델로 처리하지 않고, 저비용 모델부터 순차적으로 시도한다. 각 단계에서 실패하면 다음 단계로 넘어간다.  
- **작업 흐름:** 1) 저비용 모델 수행 → 2) 자동검증(테스트) → 3) 실패 시 동일 모델 재시도 → 4) 실패 시 중간급 모델 → 5) 실패 시 최고급 모델 → 6) 실패 시 인간 개입.  
- **장점:** 비용 절감이 가장 크다. 대부분의 간단 작업은 저비용 모델로 처리하고, 복잡한 경우에만 고성능 리소스를 소비한다. 모든 단계가 자동화되면 전체 워크플로우를 최소한의 비용으로 수행할 수 있다.  
- **단점:** 중간 단계 이동 시마다 다중 요청과 지연이 생긴다. 단계가 많아질수록 레이턴시 증가와 구현 복잡도가 커진다. 실패 판단을 잘못하면 품질 저하 위험이 있다. 또한, 연쇄적으로 여러 모델을 호출하므로 토큰 사용량이 증가할 수 있다.  
- **적합:** 비용 제약이 크고, 작업 난이도가 다양하거나 예측 불가능할 때 유리하다. 예를 들어, 대부분은 단순한 수정 작업이지만, 가끔 복잡한 버그가 나올 수 있는 경우에 적합하다.  
- **필요 기술:**  
  - 프롬프트 내 or 외부 로직으로 “이전 단계 실패 시 다음 단계 호출” 조건을 구현.  
  - 에러 감지(테스트/exit code) 후 모듈화된 재시도 메커니즘(Celery/RQ) 사용.  
  - 각 단계 별 모델 API 호출을 자동화하는 파이프라인 (예: LangChain Chain-of-Thought 모듈이나 비즈니스 로직 스크립트).  
  - 실패 조건과 재시도 제한 설정 (재귀/무한루프 방지를 위해).  

- **예제:** 고객 문의 분류 시스템에서, 간단한 문의는 경량 분류기로 처리하고, 복잡한 문의는 단계적으로 복수 분류기를 거친 후 최종 검토를 받는 방식.  

## 아키텍처 C: 분리된 작업 공간 + 통합 관리자  
```
Manager
  ├─ Worktree A + Worker A
  ├─ Worktree B + Worker B
  └─ Worktree C + Worker C
           ↓
     Test / Review Agent
           ↓
       Merge Agent
```  
- **설명:** 각 워커가 서로 독립된 Git 워크트리(분기된 폴더)에서 작업한 뒤, 관리자 또는 별도의 검증 에이전트가 이들을 통합하는 방식이다.  
- **작업 흐름:** Manager가 작업을 분배할 때 각 워커에게 고유 브랜치(worktree)로 작업하라고 지정 → 워커들이 각자 파일 수정 후 commit → (중간) 테스트/검토 단계에서 모든 워크트리를 병합(가상으로)해 충돌 검사 및 테스트 실행 → 최종적으로 Merge Agent가 병합 및 릴리즈.  
- **장점:** 작업 공간이 엄격히 분리되어 병렬 작업이 용이하고 충돌 위험이 줄어든다. 각 워커가 자신의 환경을 갖추므로 시행착오가 다른 작업에 영향을 주지 않는다. 병합 전 검증을 철저히 하면 안정성이 높다.  
- **단점:** 관리 부담이 크다. 병합 과정에서 충돌이 발생하면 해결이 복잡하고, 각 워크트리 상태를 주기적으로 동기화해야 한다. 테스트 에이전트가 중간에 모든 변경을 모아야 하므로 연산량이 늘어난다. 또한 브랜치가 많아질수록 관리가 번거로워진다.  
- **적합:** 서로 독립적인 모듈(예: 여러 독립 기능, 마이크로서비스) 개발에 적합하며, 병렬성이 극도로 중요할 때 유리하다. 팀 프로젝트의 Git 워크플로우를 철저히 모방하는 구조다.  
- **필요 기술:**  
  - `git worktree` 또는 유사 기능으로 분리된 작업 디렉토리 구축.  
  - 각 워커가 해당 워크트리에서 Claude Code를 사용하거나 CLI로 코딩 수행.  
  - 공통 테스트/CI 에이전트가 워크트리들을 sequential 또는 병렬로 체크아웃하여 테스트 실행.  
  - 병합 후 검사 및 릴리즈를 담당할 Merge Agent(관리자) 구성.  
  - 충돌 발생시 자동 알림/자동 분기 처리(예: 충돌 리포트 생성 후 팀 알람).  

- **예제:** 마이크로서비스 기반 프로젝트에서 각 서비스 기능을 별도 브랜치로 개발하고, 종합 테스트 후에 통합하는 방식. 다수의 개발자(에이전트)가 독립적으로 작업하고, 마지막에 CI 서버가 종합하는 형태를 흉내 낼 수 있다.  

> **아키텍처 비교:** 각 구조는 서로 장단이 있으며, 특정 문제에 맞는 아키텍처를 선택해야 한다. 예를 들어, A 구조는 단일 포인트에 결과를 모아보기 쉽지만, 멀티스레드 상황에선 병목이 될 수 있다. B 구조는 비용 최적화에 강하지만, 레이턴시와 복잡도가 상승한다. C 구조는 충돌 방지에 유리하지만 설정과 유지보수 오버헤드가 크다. 실제로는 이들 요소를 혼합하거나, 상황에 따라 Adaptive하게 변경하는 하이브리드 전략도 고려해볼 수 있다.  

# 12. 관련 구현 사례 조사  
공개된 자료를 통해 **Claude Code 자체 또는 이와 유사한 개념**으로 여러 모델 계층을 구현한 사례를 찾아보았다. 구체적인 Claude Code 기반 프로젝트는 아직 등장하지 않았으나, 일반적인 멀티에이전트 사례 및 Claude 유사 구조는 몇 가지 확인된다.  

- **LangChain Agent 예제:** LangChain 문서와 커뮤니티에서 ‘Agent of Agents’ 패턴을 소개하고 있다. 예를 들어 [LangChain 공식 예제](https://python.langchain.com/docs/use_cases/agent_of_agents)에서는 하나의 “Master”가 다른 “Tool Agents”에 질의를 분배한다. 이때 모델 교체나 Escalation은 수동 정의지만, 개념적으로는 이번 연구의 구조와 유사하다. 최근에는 LangChain을 이용한 코드 에이전트 예제(타코 개발 코드 생성 등)도 올라왔다.  
- **AutoGen 다중 에이전트 대화:** Meta의 AutoGen에서는 여러 개의 GPT 봇이 협업하여 복잡한 태스크를 해결하는 예제를 발표했다. 예를 들어 고객 문의를 처리하는 시나리오에서, 테스크 관리자와 토픽별 챗봇들이 역할을 나눠 대화를 진행한 바 있다. 아직 구체적인 코드워크플로우 예제는 적지만, 메타가 제시한 프레임워크를 Claude 에이전트로 대체해볼 수 있다.  
- **MetaGPT 프로젝트:** Microsoft Research의 [MetaGPT GitHub](https://github.com/microsoft/MetaGPT)을 보면, 소프트웨어 개발을 위한 멀티에이전트 예제가 있다. 이 프로젝트는 요구사항 분석, 설계, 코딩, 테스트를 담당하는 에이전트를 정의한다. 실제로 GitHub 이슈로 Claude나 GPT를 에이전트로 사용한 사례가 올라오기도 했지만, 대부분 GPT-4 기반이다. 라이선스는 MIT이며, 코드 자동 생성 및 에이전트 간 메시징 구조가 잘 정리되어 있다.  
- **Agentic 도구:** CrewAI나 SWE-Agent 같은 신생 프로젝트들이 있는데, 예를 들어 CrewAI는 연구 논문 형태로 “Agentic Assistant”를 제안하고 LLM 에이전트를 순차/병렬로 조합하는 예제가 있다. 이런 프레임워크는 Claude 지원 여부는 불분명하지만, 오픈소스로 커스터마이징 가능하다. 일반적인 메이저 사례는 많지 않으나, AI 개발 커뮤니티(Hacker News, Reddit)에서 “LLM agent supervisor” 관련 논의가 활발하다.  
- **GPT-4 로봇 예시:** OpenAI 발표 자료에서 GPT-4가 여러 서브 에이전트를 활용해 코딩 임무를 해결한 시나리오가 소개된 적이 있다. 이는 Claude Code가 직접 아닐 수 있지만, 유사한 계층형 아이디어를 실험했다는 점에서 참고할 만하다.  
- **운영사례:** 유사한 개념으로, 소프트웨어 회사들이 “LLM + CI/CD” 자동화 사례를 블로그에 공유하기도 했다. 예컨대, aiOps툴이 코드 PR 리뷰를 LLM에 맡기는 형태가 대표적이다. Claude Code 전용 예제는 아니지만, 이들은 LLM이 “코드 변경 → 테스트 → 병합” 사이클에 들어가는 패턴을 보인다.  

> **요약:** Claude Code 자체 관련 오픈소스 사례는 아직 미미하나, LangChain/AutoGen/MetaGPT 등의 일반 LLM 에이전트 사례에서 아이디어를 차용할 수 있다. 실제 구현은 Claude API나 유사 Claude 모델로 에이전트 역할을 대신하면서, 위 프레임워크들을 활용하는 방식이 유력하다. Claude 전용 사례가 등장하면 유사도 조사해 통합할 수 있다.  

# 13. “가능성” 수준 분류  
다음 질문들에 대해, **기능 구현의 가능성 정도**를 7단계로 나누어 평가한다. 가능/불가능을 넘어서 현재 기술이 어느 수준까지 허용하는지 명확히 구분했다.  

| 질문                                                         | 결론 수준                                | 근거 및 비고                                              |
|------------------------------------------------------------|----------------------------------------|-----------------------------------------------------------|
| 최상급 모델이 하위 모델을 직접 관리할 수 있는가?                | **불가능 (현행 기능 없음)**              | Claude Code 자체에 agent간 호출 기능 없음. 외부 스크립트로만 가능. |
| 서로 다른 모델을 역할별로 배치할 수 있는가?                     | **가능 (API 조합 시)**                  | 한 세션 내 모델 전환은 불가하지만, API로 별도 호출 조합은 가능. |
| 하위 모델이 직접 파일을 수정하고 테스트할 수 있는가?            | **가능 (클라우드 환경 내)**             | Claude Code는 파일 편집·터미널 실행 지원. 다만 병렬 충돌 통제는 수동. |
| 작업 실패를 자동으로 감지할 수 있는가?                        | **부분 가능 (외부 구현 필요)**         | Claude Code에는 실패 트리거 기능 없음. 테스트/exit code 활용은 가능. |
| 실패 시 최상급 모델로 자동 Escalation 가능한가?                 | **불가능 (현행 기능 없음)**              | Claude Code 내부에서 조건부 전환 지원하지 않음. 스크립트로만 가능. |
| 최상급 모델이 이전 작업 로그와 코드 변경을 이해할 수 있는가?     | **가능 (정보 제공 필요)**               | 입력으로 로그/코드 전달하면 이해 가능. 다만 직접 DB 연결은 불가. |
| 여러 하위 모델을 병렬로 실행할 수 있는가?                       | **불가능 (현행 기능 없음)**              | Claude Code 세션은 기본적으로 단일 흐름. 여러 세션 별개로 운용하는 것은 가능. |
| 작업 공간을 분리할 수 있는가?                                 | **부분 가능 (외부 관리 필요)**         | Claude Code 내에서 작업 공간 분리 기능 없음. Git worktree 등으로 우회 가능. |
| 비용과 재시도 횟수를 제어할 수 있는가?                         | **가능 (API 모니터링 시)**             | API 호출 시 비용/토큰 사용량을 계산해 제어 가능. 자동 제한은 지원 안됨. |
| 사용자 승인 없이 완전 자동 실행이 가능한가?                    | **부분 가능 (위험**함)**               | 기술적으로는 가능하지만 안전 상 권장되지 않음. 무인 자동화를 위해선 권한/안정성 확보 필요. |

- 각 항목에 **가능/불가능** 여부를 개략적으로 결론지었다. 예를 들어, “하위 모델 직접 파일 수정”은 Claude Code 자체 기능으로 제공되므로 가능하지만, “다른 모델 자동 전환”은 지원되지 않아 불가능으로 분류한다.  
- **근거 수준:** 명시된 기능은 [FACT]나 Anthropic 문서에 기반하며, 미공식 기능은 [UNKNOWN] 또는 [INFERENCE]로 구분했다. 예를 들어, 멀티모델 세션 전환이 지원되지 않는 것은 공식 부재를 근거로 [UNKNOWN]으로 표시했다.  
- **추가 확인:** 실제 프로덕션 환경 적용 시, 위 항목별로 (a) 공식 업데이트로 가능해졌는지, (b) Anthropic 라이브러리 업데이트가 필요한지 등을 검토해야 한다.  

# 14. 최종 기술 지도 (체계도)  
지금까지 조사한 기술과 모델들을 **계층적 플로우** 형식으로 정리한다. 아래 다이어그램과 표에서 각각의 요소가 공식 지원되는지, 외부 구현이 필요한지 구분했다.  

```
                   User Request
                        │
                        ▼
                Manager / Supervisor    <─ 주 모델(Claude, GPT 등) [공식]
                        │
               Task Decomposition (외부 Orchestrator 필요)
                        │
      ┌─────────────────┼─────────────────┐
      ▼                 ▼                 ▼
   Worker A          Worker B          Worker C    <─ 보조 모델 or 동일 모델 [외부 구현]
  (Coding)          (Testing)        (Research) 
      │                 │                 │
      └─────────────────┼─────────────────┘
                        ▼
             Validator / Tests (추가 모델 세션 or 스크립트)
                        │
              ┌─────────┴─────────┐
              │                   │
            Success            Failure
              │                   │
          Next Task          Retry / Reroute
                               │
                         Escalation logic
                               │
                      Advanced Manager (최상급 모델) 
                               │
                            Human Review
```

- **User Request:** 사용자 입력(기능 설명, 버그 리포트 등).  
- **Manager/Supervisor:** 최상위 에이전트. Claude Code(클라우드 모델)나 외부 호출 모델. 업무 분해와 결정을 담당.  
- **Task Decomposition:** Manager가 해야 할 작업을 서브태스크로 분리. **외부 Orchestrator**(LangChain, 스크립트)가 이 기능을 수행. Claude Code 단독으로는 추론 수준에서만 분해 가능하다.  
- **Worker A/B/C:** 코드 작성, 테스트, 자료조사 등을 담당하는 에이전트. Claude Code 내 세션(동일 모델)일 수도 있고, 각기 다른 경량 모델 세션이 될 수도 있다.  
- **Validator/Tests:** 모든 Worker 결과에 대한 검증 단계. 테스트는 자동화 스크립트 혹은 별도의 검증 모델이 수행. Claude Code로 테스트를 실행할 순 있어도, 결과 판단 로직을 갖추진 않음.  
- **Success:** 정상 완료된 태스크는 다음 단계나 새로운 Task로 넘어간다.  
- **Failure → Retry/Reroute:** 실패 시 같은 워커에게 재시도하거나 다른 워커(모델)에게 넘긴다. 자동 조건부 전환 로직은 외부 개발 필요.  
- **Escalation:** 반복 실패 시 중간-상위 모델로 승격. 관리자가 직접 개입하거나, 코드에 수정 지시를 내린다. Claude Code API 호출로만 가능하며 자체 지원 기능은 없다.  
- **Advanced Manager:** 문제 해결이 계속 안 되면, 고성능 모델(Claude Max, GPT-4o 등)에게 맡긴다. 이때까지의 로그와 코드를 모두 제공해야 한다.  
- **Human Review:** 자동화로 해결되지 않는 경우, 최종적으로 개발자나 관리자 승인이 필요하다. 이 부분은 완전 자동화가 불가능하며, 시스템 디자인에서 ‘인간 개입’ 포인트로 명확히 구분해야 한다.  

각 요소 옆에 기술(모델/도구)이 실제로 사용 가능한지 표기했다. 예를 들어, Manager는 `Claude API` 또는 `GPT-4 API` 같은 공식 모델 호출로 가능, Worker는 경량 Claude나 오픈소스 LLM(LOCAL 실행)도 가능하다. Task Decomposition과 Escalation 같은 로직은 `LangChain/AutoGen` 같은 오케스트레이션 도구를 추가해야 구현된다.

## 결론 요약  
현재 Claude Code를 이용해 완벽한 계층형 에이전트 시스템을 **단독으로** 구축하는 것은 많은 제약이 따른다. 본 연구를 통해 알게 된 바는:  

- **공식 기능 한계:** Claude Code는 강력한 코드 에디터와 실행 환경을 제공하지만, 서브에이전트, 조건부 전환, 다중 세션 조율 같은 멀티에이전트 기능은 제공하지 않는다. 주요 기능(파일 편집, 코드 실행, 단일 세션 대화)은 **[FACT]**로 확인되지만, 멀티모델 협업은 문서화되지 않았다.  
- **외부 보완 필요:** 다양한 모델을 역할별로 조합하려면 Claude API를 외부에서 호출해야 한다. LangChain, AutoGen, Celery, Docker 등 오픈소스 툴을 결합하여 컨트롤 플로우를 작성해야 한다. 예: Python 스크립트로 저비용 모델→테스트→고비용 모델 호출 로직을 구성한다.  
- **주요 제약:** 오류 감지/승격 로직과 병렬 작업 관리는 개발자가 설계해야 하는 영역이다. 예를 들어, 실패 조건 판단, 재시도 횟수 제어, 작업 공간 분리는 모두 직접 구현해야 한다. Claude Code가 제공하는 건 `러닝 모델 + 실행 환경`이고, *자동 협업 관리*까지 보장해주진 않는다.  
- **운영 복잡성:** 멀티에이전트는 단일 모델보다 복잡성을 크게 증가시킨다. 추가적인 코드 인프라(오케스트레이터, DB, CI)가 필수다. 따라서 모든 작업을 전자동화하기보다는, 핵심 업무에만 에이전트를 사용하고 인간-검증 단계를 명확히 두는 것이 안정적이다.  
- **조합적 장점:** 그럼에도 불구하고, 작은 모델들을 조합함으로써 발생할 수 있는 비용 절감과 안전성 증대라는 장점은 분명하다. 특히 저비용 모델이 효율적으로 선별 작업을 처리하게 하고, 불확실할 때만 큰 모델로 넘기는 구조(B 및 C)가 실제 구현 가치가 있다.  

종합적으로, **“최상급 모델 하나 vs. 작은 모델 여러 개”** 문제는 단순 비교가 아니라 운영·비용·신뢰도의 복합 평가이다. 현재 기술력으로는 완전 자동화는 어렵지만, 적절한 오케스트레이션과 사람의 개입을 조합하면 계층형 협업 시스템을 부분적으로 구현할 수 있다. 결국 프롬프트 엔지니어링, external tooling, 검증 체계 세팅 등을 통해 필요한 만큼 시스템을 확장해 나가는 수밖에 없다.
